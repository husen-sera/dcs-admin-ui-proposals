DCS / Admin panel · Proposal

Modernizing the Django
admin with free OSS

We want to make user-activity analysis easier. The admin UI is the foundation that has to be modernized first. Here are three options, each shown against DCS's own screens. Please pick one.

ClickUp z94amcqevr Owner Husen Approver Coco Drafted 2026-10-15 License MIT (commercial use OK) — all three

Summary

The short version

  • We re-skin the admin with a free, commercially-licensed (MIT) OSS library. The candidates are A: django-unfold, B: django-jazzmin and C: django-admin-interface.
  • The goal this time is the look only. Every existing admin feature must keep working exactly as it does today; new charts and dashboards are deliberately split into a follow-up ticket.
  • DCS runs Python 3.9, so none of the three can use its latest release — each gets pinned one version back. That is the only technical constraint, and it is covered below.
What we need from you: choose one of A / B / C. Once it is approved we start implementing. From approval to handing it over for UAT we estimate roughly 4 working days for A, 2.5 for B, or 1.5 for C.

Constraint

Python 3.9 — the one thing to know up front

DCS runs on Python 3.9 with Django 4.2. Over the last year or two, every major admin-theme library has raised its Python floor to 3.10 or higher, which means no option can use its latest release. Verified against PyPI today:

LibraryLatestLatest requiresLast release usable on 3.9License
django-unfold (A)0.110.0Python ≥ 3.12 0.67.0 states 3.9 supportMIT
django-jazzmin (B)3.0.5Python ≥ 3.10 3.0.1 states 3.9 supportMIT
django-admin-interface (C)0.32.0no floor declared 0.32.0 needs verifyingMIT
django-baton5.9.3Python ≥ 3.10 5.4.1 needs verifyingMIT
django-jet-reboot1.3.10—— AGPLv3 / non-commercial

django-jet-reboot is ruled out — it is AGPLv3 and licensed "free for non-commercial use", which fails the requirement that the library be free and licensed for commercial use.

What this means in practice: whichever library we choose stays pinned at that version and stops receiving upstream fixes. Upgrading Python to 3.12 would clear this, but it also means re-pinning pandas / numpy / reportlab and re-running the whole test suite — so it belongs in a separate ticket. We are not touching it here.

Option A / django-unfold — the summary page. The stat cards and tables can be rebuilt from unfold's own components.

Strengths

  • The only one of the three whose own metadata declares Python 3.9 support
  • Ships chart, table and card components, so the follow-up dashboard ticket lands straight on top of it
  • Zero additional dependencies — the smallest possible blast radius
  • Dark mode, richer filters, ⌘K search

Cost and caveats

  • All 13 registered admin classes must be switched to unfold's base class
  • The user, group and scheduled-task screens need re-registering, or they render unstyled
  • Some of the theme's own labels will have no Japanese translation
  • Longest implementation of the three (~4 working days)
Why we recommend it: it is the only option that both provably runs on Python 3.9 and gives us the foundation for the analytics dashboard that prompted this ticket. The higher migration cost is recovered by the next ticket.

Option B / django-jazzmin — the summary page, inside a Bootstrap card.

  • Looks distinctly "Bootstrap"; less contemporary than A

Option C / django-admin-interface — the summary page. The layout is identical to today's.

Strengths

  • The layout does not move, so every existing workflow still applies
  • Colours and logo are editable from inside the admin — no deploy per tweak
  • Smallest impact on our existing custom pages, such as the summary screen
  • ~1.5 working days to implement

Cost and caveats

  • Python 3.9 support is unconfirmed — its metadata assumes 3.10+, so this needs testing first
  • Two extra dependencies (django-colorfield, python-slugify)
  • Stores the theme in the database, so it adds a migration
  • The weakest answer to "modernize the UI" of the three

Audience

Who sees this change

In every option, the only UI that changes is /admin/. The DCS product itself (the SPA) is completely untouched. One thing worth flagging first, though: the admin is not purely internal.

  • The accounts that can reach the production admin include administrator accounts belonging to the client, not only our own staff (exact figures and addresses are in the ClickUp ticket).
  • Because of that, the two activity-log screens stay internal-only — they are gated by an email allowlist, and we are not changing that gate in this work.
  • Every other admin screen is already visible to the client side, so the visual change will be too.
Decision needed: whether the client should be notified in advance. If so, we will add it to the pre-release checklist.

Risks

What we are watching for

RiskMitigation
The user edit form breaks — DCS stores group membership differently from stock Django Don't just open the form; save it as part of the verification pass. The riskiest single edit in option A.
Tests silently stop asserting anything once the theme renames the HTML they look for Rewrite those tests first, on the current theme, and confirm they are green before the theme goes in.
The internal-only gate on the activity log comes loose Log in as a non-allowlisted account every time and confirm the section is absent and both pages return 403.
Static files (CSS/JS) are not served in production Verify on both staging and production after deploy — the web-server config lives outside the repo, so fixing one box does not fix the other.
One scheduled-task screen exists only in production and cannot be checked on staging Cover it with tests and confirm visually right after the production release.
