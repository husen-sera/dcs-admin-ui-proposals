Summary

The short version

  • Three libraries were shortlisted. django-jet-reboot had to be dropped — it is AGPLv3 and its own packaging says "free for non-commercial use", which fails this project's licensing requirement outright. That leaves two.
  • A — django-unfold is the more polished product and the better foundation for the analytics dashboard we want next. It must be pinned to an older release to run on our Python.
  • B — django-daisy is the only candidate that runs its current release on our Python, and it needed no code changes at all to work.
  • Both were installed and driven for real. In both, the user edit form saved correctly — the single thing most likely to have broken. In both, one custom screen needs restyling.
What we need from you: choose A or B. From approval to UAT we estimate ~4 working days for A or ~2 days for B.

Strengths

  • The most finished-looking of the two, with dark mode and a command palette
  • Ships chart, table and card components, so the follow-up dashboard builds on it directly
  • Zero runtime dependencies
  • Large, actively maintained project (1M+ installs/month)

Cost and caveats

  • Pinned to 0.67.0 (Sep 2025) — the current release needs Python 3.12, so we get no upstream fixes
  • Every one of our 13 admin classes must be changed to inherit Unfold's base class
  • The user/group screens need re-registering with Unfold's own forms
  • Our two custom buttons and the 期間 filter need restyling

Login.

Strengths

  • Runs its current release on our Python — the only candidate that is not frozen
  • Needed no changes to any admin class; installation is configuration only
  • Built-in theme switcher, so colours change without a deploy
  • Supports Django 3.2 all the way to 6.1, so it will not block a future Django upgrade

Cost and caveats

  • A younger, smaller project than Unfold — fewer users, fewer maintainers
  • No chart components, so the follow-up dashboard would be built from scratch
  • Requires adding django.contrib.humanize (a Django built-in we do not currently enable)
  • The dense activity-log table wraps more than under Unfold; our 期間 filter still needs restyling
  • Its licence is stated two ways — LICENSE says MIT, packaging says Apache-2.0. Both allow commercial use.

Rejected

Evaluated and not proposed

LibraryWhy not
django-jet-reboot 1.3.10 Licensing. It is AGPLv3, and its own packaging declares "Free for non-commercial use" — which fails our requirement that libraries be free and licensed for commercial use. AGPL also carries a network-use clause that can oblige publishing source for a service we expose to users. Separately, it has no working demo: the original project's demo site is offline and its screenshots are from the predecessor project. repo · docs
django-jazzmin 3.0.1 Permissively licensed, but its last release compatible with our Python is from October 2024, and it moves list filters into header dropdowns, so our custom filter would need porting anyway. Daisy covers the same ground while staying current.
django-admin-interface 0.32.0 Permissively licensed, but declares no Python floor and its metadata targets 3.10+, so support for our Python is unverified. Adds two dependencies and a database migration, and changes the least visually.

Constraint

Why versions matter here

DCS runs Python 3.9. Most Django admin themes have raised their minimum Python past that, so for most candidates we would be stuck on an old release with no upstream fixes. That is the single biggest difference between the two options:

  • Unfold — current release requires Python 3.12. We would run 0.67.0, the last release that supports 3.9, and stay there until Python is upgraded.
  • Daisy — supports Python 3.8+ and Django 3.2–6.1, so we run the current release and keep receiving updates. Verified by installing it on our actual Python and compiling the package.
Upgrading Python 3.9 → 3.12 would remove this constraint entirely, but it means re-pinning several numerical and PDF libraries and re-running the whole test suite. It is a separate ticket, not part of this work. Choosing Daisy makes it less urgent.

Audience

Who sees this change

Only /admin/ changes. The DCS product itself is untouched. One thing to note: the production admin is not purely internal.

  • Accounts that can reach the production admin include administrator accounts belonging to the client, not only our own staff (figures are in the ClickUp ticket).
  • The two activity-log screens stay internal-only — they are gated by an email allowlist that this work does not change.
  • Every other admin screen is already visible to the client side, so the visual change will be too.
Decision needed: whether the client should be told in advance.
